# 界面模型：单文件、选项式（设计）

状态：已与用户确认方向（2026-11）。**阶段 A 已完成并经真机确认**（测试包 1.36.0）；**阶段 B 已实现**（测试包 1.37.0，用户确认行为符合预期）；**阶段 C 已完成**（测试包 1.41.0 真机：连续点击不再吞掉）；**事件总线与合并队列已实现**（待真机确认，测试包 1.42.0）；阶段 D、E 未开始。

## 1. 要求（来自用户）

1. 控件仍是面向对象的（`new Label(…)`、`setXxx()`）；不要像 JSON 那样纯数据驱动。
2. **一个界面写在一个文件里**：视图与逻辑在同一个文件中，但分成清楚的几块、互不耦合（类似 Vue 的单文件组件）。选项式（Vue 2）为主，以后可以加组合式（`setup()`）。
3. 使用者**接触不到按钮序号与标记**：按钮用名字，由框架映射序号。
4. 不用全局的 `form` 对象：数据的来源与归属要一眼可见。
5. 引入更健康的写法：响应式状态、生命周期、视图与逻辑分离。

## 2. 讨论过、被否定的方案

| 方案 | 否定的原因 |
|---|---|
| 全局 `form`（`form.text`、`form.button(n)`） | 不知道它是哪个表单、和哪个界面绑在一起；按钮相关的读取只在特定容器内有效，写法上看不出 |
| `defineScreen((form) => …)` 里用 `form.value(名字)` 返回一个「装着值的容器」 | 把游戏的技术限制（按钮数据只能在对应的容器内读取）暴露给使用者；`form.value` 是什么讲不清 |
| 在函数顶部用 `form.text('x')` 声明数据 | 新手想不到要先在 `form` 上声明，会直接写普通变量 |
| 隐式 props（用到 `props.x` 就算定义） | 不知道界面接收哪些数据；界面里拼错名字会悄悄多出一个 prop |
| `defineScreen(fn).defineProps({…})` 链式 | 定义、视图、按钮挤在一个调用里 |
| 界面类（`class Shop extends Screen`）＋ 脚本端的逻辑类，分两个文件 | 视图与逻辑跨文件，不好沟通 |

## 3. 运行时间与地点（决定了设计的边界）

| | 视图（`view`） | 逻辑（`state`、`computed`、`methods`、生命周期） |
|---|---|---|
| 何时运行 | **构建时**运行一次，编译为 JSON UI | **游戏运行时** |
| 在哪里运行 | Node（构建工具）；编译结果在客户端显示，客户端不能运行 JavaScript | 行为包脚本（QuickJS） |
| 能用什么 | `props`（占位，编译为绑定）、`button(名字)`、`pages(组名)`、控件 | 状态、玩家对象、游戏的脚本 API |

两者之间唯一的通道是服务端表单：逻辑 → 视图是打开表单时的标题、正文与按钮；视图 → 逻辑是玩家点击了哪个按钮。表单打开后内容不能修改，**更新 = 关闭后以新内容重新打开**（翻页已验证可做到鼠标不动连续点击）。

不能做到的：表单打开期间实时更新内容、实时的双向绑定（只有 DDUI 能做到，见 §9）。

## 4. 写法

```js
// ui/shop.screen.js
import { defineScreen, Anchor, Image, Label, Panel } from 'bedrock-cui'

export default defineScreen({
    id: 'cui_ui:shop',

    // ———— 数据：视图接收的 props 与默认值 ————
    props: {
        greeting: '欢迎光临',                                         // 文字
        item: { text: '钻石', icon: 'textures/items/diamond' },        // 文字与图标
    },

    // ———— 逻辑：在游戏中运行 ————
    state() { return { coins: 10 } },
    computed: {
        greeting() { return `金币：${this.coins}` },                  // 与 props 同名：由状态计算该 prop
    },
    methods: {
        buy() { this.coins -= 1 },                                    // view 中 button('buy') 被点击时调用
    },
    onOpen() { },
    onClose() { },

    // ———— 视图：返回控件树（构建时运行） ————
    view({ props, button, pages }) {
        return new Panel().setSize(200, 120).add(
            new Label(props.greeting).setSize(180, 10).setAnchor(Anchor.TOP_LEFT),
            new Image(props.item).setSize(16, 16),
            new Label(props.item).setSize(120, 10).setOffset(20, 0),
            button('buy').setSize(60, 18).setAnchor(Anchor.BOTTOM_RIGHT),
        )
    },
})
```

```js
// cui.config.mjs
import shop from './ui/shop.screen.js'
export default defineConfig({ namespace: 'shop', screens: [shop] })
```

```js
// scripts/index.js：只决定什么时候打开
import shop from '../ui/shop.screen.js'

```

## 5. 各部分的规则

### 5.1 `id`
界面 id，必须以 `cui_ui:` 开头。

### 5.2 `props`
- 定义视图接收的数据，值为默认值。默认值的类型决定 prop 的种类：字符串（文字）；`{ text, icon }`（文字与图标）；数组（列表，元素为前两种之一，长度为最大项数）；布尔值（是否显示）。
- 一个 prop 的值，按以下顺序取第一个有的：`computed` 中的同名项 → `open(玩家, { … })` 传入的值 → 默认值。
- 浏览器预览使用默认值。

### 5.3 视图 `view({ props, button, pages })`
- 构建时调用一次，返回控件树。不能访问 `state`、`methods`。
- `props.x` 是占位（表达式），可用于：`Label` 的文字（取 prop 的文字）、`Image` 的贴图（取 prop 的图标）、`setVisible()`（prop 有值时显示）。列表用 `props.items[i]`。
- 使用 `props` 中没有定义的名字 → 静态检查报错（例：拼成 `props.greting`）。
- 显示 prop 的控件需要**像素尺寸**（读取按钮数据的方式决定），否则静态检查报错。
- 一个控件只用一个 prop（同时用两个 → 静态检查报错，提示拆成嵌套的两个控件）。
- `button(名字)` 返回可点击的按钮（`default`、`hover`、`pressed` 三个状态面板）。名字必须在 `methods` 中有同名方法，否则构建报错；同一名字只能创建一次。
- `pages(组名)` 返回 `Pages`；其中的服务端翻页箭头由框架处理，不需要在 `methods` 中写任何东西。

### 5.4 逻辑
- `state()` 返回初始状态。**每个玩家一个实例**：`shop.open(玩家)` 时创建（已打开则复用），关闭时销毁（`onClose` 之后）。
- `this`：可以读写状态（`this.coins`）、读 `computed`、调用 `methods`、`this.player`（当前玩家）、`this.close()`。
- `computed` 只用于计算 props（与 props 同名）；不同名的 computed 视为辅助值。
- `methods` 中与 `button()` 同名的方法在点击时调用；其他方法是普通的辅助方法。
- 生命周期：`onOpen()`（第一次打开前）、`onUpdate()`（点击按钮、方法执行完之后，重新打开之前）、`onClose()`（玩家按 Esc 关闭，或调用 `this.close()`）。
- **状态变化 → 重新打开**：方法或生命周期执行完后，若状态有变化，重新计算 props 并重新打开表单；同一轮的多次修改只重新打开一次。重新打开时，刚才点击的按钮获得默认焦点（与翻页相同的做法：每个按钮编译为普通版与聚焦版两个同序号按钮），鼠标不动也能连续点击。
- 遵守已知的真机规则：重新打开的过程中不向聊天栏发消息、不重复设置输入权限。

## 6. 编译：名字到序号

每个界面一个分配器：先按 props 定义的顺序分配（每个 prop 一个按钮，列表每项一个）；之后按创建的先后分配给 `button()`、翻页箭头与「原地不动」。构建生成的清单（写进 `cui.generated.js`）：

```js
{ id: 'cui_ui:shop', props: [{ name: 'greeting', index: 0, kind: 'text' }, { name: 'item', index: 1, kind: 'item' }],
  buttons: [{ name: 'buy', index: 2 }], paging: null }
```

- prop 的按钮文字为 `「标记」+ 文字`，标记由框架生成（例：`p0|`），视图显示时去掉；图标即按钮的图标。
- 视图中使用 prop 的控件，编译时自动包上读取对应按钮的容器（现在的 `CollectionItem` 编译方式，已真机验证），容器的尺寸与位置取自该控件。
- 使用者看不到 `form_buttons`、序号、标记、`CollectionItem`、`FormButton`、`ServerPagesForm`；它们成为内部实现。

## 7. 运行时

- `bedrock-cui/runtime/screens`：`defineScreen()` 在行为包中返回界面对象（`open`、`close`、`isOpen`）。打开时按清单生成 `ActionFormData`：标题 = 界面 id（翻页时附页名），正文为空，按钮按序号填入 props 的值与按钮的标记。
- 清单由 `cui.generated.js` 注册（脚本入口需要导入一次；构建时检查）。
- `bedrock-cui` 主入口的控件类会随视图代码进入行为包（视图不在运行时执行）。体积与 QuickJS 的加载耗时需实测；必要时在构建时去掉视图部分（见 §9）。
  实测（模板改用 defineScreen 后）：行为包脚本 187.7 KB（含控件类与 Unifont 字宽表），附加包 214 KB（此前约 93 KB）。
  优化（2026-11）：Unifont 字宽表改为游程编码、首次查询时解码（64 → 30.7 KB）；开发模式 160.7 KB，生产模式（sapdon buildMode prod，terser 压缩）79.3 KB。
  构建期模块（编译器、静态检查、排版引擎、预览、富文本、字形图）已被 rollup 摇掉；剩下的是运行时、控件类，以及 Paragraph 引用的字宽表与游戏字形表。
  sapdon 的 rollup 插件列表固定（nodeResolve、commonjs、json，prod 时 terser），无法加入「去掉视图」的插件。

## 8. 预览

`bedrock-cui dev` 用 props 的默认值显示视图。逻辑是普通的 JavaScript，也可以在浏览器中运行：点击按钮 → 调用方法 → 状态变化 → 重新计算 props → 预览更新，在浏览器中就能试完整的交互。

## 9. 未决的问题

- **视图代码进入行为包**：sapdon 的 rollup 配置不由 CUI 控制，无法直接加去掉视图的转换。先实测体积与加载耗时，再决定（可能请 sapdon 提供插件钩子）。
- **输入控件**：`ModalFormData`（文本框、滑块、下拉框、开关）的值在提交时传回脚本。能否像 `ActionFormData` 一样改写外观，需研究原版界面定义并真机测试。
- **实时更新与双向绑定**：只有 DDUI（`CustomForm`、`ObservableString` 等，`@minecraft/server-ui` 2.2.0 起）能做到，外观由 Ore UI 绘制。可评估为 DDUI 另做一层类 Vue 的写法。
- **组合式**：`setup()` 写法在选项式稳定后再加。
- **界面内部的状态**（标签页、展开折叠）：用开关在客户端切换，不经过脚本。写法（类似 `v-model` / `v-show`）待设计。

  已记入手册的真机规则。`showForm()` 的 UserBusy 重试是否必要未经证实，保留（无害）。

## 14. 阶段 B 的真机反馈与阶段 C

- 1.37.0：用户确认行为符合预期。用户问到「关闭后再打开，计数从 0 开始」——预期内：state 每次打开时由 state() 新建、关闭时销毁（同 Vue 组件卸载后再挂载）。
  跨越多次打开的数据（如金币）放在界面之外（脚本变量、玩家的动态属性），打开时经 open(玩家, props) 传入或在 onOpen 中读取。以后若常见，可加保留状态的选项。
- 阶段 C（1.38.0）：界面以外的状态变化触发刷新——ctx 的写入在不处理点击时安排刷新（platform.schedule，合并到下一刻）：关闭当前表单（closeAllForms）、
  以新的状态重新打开，焦点不变，不调用 onClose；`this.refresh()` 手动刷新；状态检测是浅层的（重新赋值才触发，同 Vue 2）。
- 定时器 `this.setInterval(函数, 刻数)`、`this.setTimeout(函数, 刻数)`：与界面生命周期绑定，关闭时自动取消；返回取消函数。
- **发现**：`@minecraft/server` 只有类型声明，Node 中导入失败；界面文件在构建时被 Node 导入，所以**不能在开头导入游戏的脚本模块**。
  定时器因此由运行时提供。与游戏交互的操作（给物品、扣金币）**提议**用 Vue 的 emit：界面中 `this.emit('buy', 物品)`，脚本中 `shop.on('buy', (玩家, 物品) => …)`——待用户确认。
- 测试 99 条（阶段 C 2 条）。演示：「倒计时」按钮，5 秒倒计时每秒更新界面。

### 阶段 C 真机反馈（1.38.0）与刷新方式的比较（1.39.0）

- 用户：倒计时进行中同时点击「点我」时显示正常；只让它倒计时，界面每秒闪烁一次。
- 分析：点击引起的重新打开是「点击即关闭 + 同一刻发出新表单」，几乎无缝；刷新是 `closeAllForms()` 后**等旧表单的取消结果传回**再显示新表单，多一次往返。
- 实验（1.39.0）：`ScreenRuntime.refreshMode` ——`wait`（原方式）/ `replace`（关闭后同一刻立即显示新表单，旧表单迟到的结果按显示编号忽略）。
  风险：服务端若仍认为旧表单开着，新表单以 UserBusy 被拒、经 showForm 重试，可能更慢。测试脚本 `/scriptevent cui:refresh wait|replace` 切换，请用户比较闪烁。
- 结论待定后：保留更好的一种作为唯一行为，删除另一种与切换命令。若两种都闪烁明显：自动刷新只适合偶尔的数据更新，高频显示（每秒倒计时）需另想办法（例如 DDUI 的 Observable）。
- 1.39.0 真机：replace 不闪烁，但同样的点击速度下「点我」只有约一半有响应。原因：旧表单被替换后，迟到的结果一律忽略——包括玩家在那一刻的点击。
  wait 方式也有同样的漏洞（关闭期间的点击被忽略），只是窗口小。修正（1.40.0）：旧表单迟到的**取消**忽略，迟到的**点击**照常处理（调用方法、获得焦点），
  再立即替换正在显示的表单；wait 方式关闭期间的点击同样处理。缺省改为 replace。测试 101 条。
- 1.40.0 真机：好多了，仍有很小的概率吞掉点击。分析：刷新是「关闭再打开」，两者之间若恰好点击，客户端没有可点的表单、根本不会发出点击——
  这一部分无法由脚本补救，只能减少碰撞。处理（1.41.0）：
  - 表单显示后 `quietMs`（400 毫秒）内推迟刷新：玩家连续点击时，每次点击本来就以最新状态重新打开，定时器的更新随下一次点击显示，不必再插入刷新；
  - 记录上次显示之后状态有无变化（dirty）：推迟的刷新到期时，若期间已因点击重新打开、之后又没有新的变化，跳过（少一次关闭再打开）；`this.refresh()` 强制刷新；
  - `showForm()` 的 UserBusy 重试间隔由 2 刻缩短为 1 刻。测试 102 条。

## 15. 事件总线与合并队列（1.42.0）

- 1.41.0 真机：这次测试没有吞掉点击。用户建议：加类似事件总线或微任务队列的机制，尽可能把同时发生的事情合并在一起运行，再尽可能加快页面开关。
- **事件总线**（即此前提议的 emit，用户以此形式认可）：界面逻辑中 `this.emit(事件名, …)`；行为包脚本中 `screen.on(事件名, (玩家, …) => …)`、`screen.off()`。
  监听函数存在界面对象上（核心模块，不依赖游戏接口）。处理函数依次执行，可为异步；出错只打印警告，不影响界面。
- **合并队列**：状态修改、`this.refresh()`、`this.emit()`、对已打开界面的 `open()` 都只标记并入队；当前代码执行完后（微任务，不再等下一刻）一次处理：
  先把事件交给脚本，再在有变化时刷新一次（仍遵守 400 毫秒的推迟）。点击时的顺序：方法 → 事件交给脚本 → onUpdate → 只重新打开一次。
- 删除刷新的 wait 方式与切换命令（replace 经真机验证不闪烁、配合推迟不吞点击），只保留一种行为。
- 加快开关：刷新的合并从「下一刻」提前到「当前代码执行完」；showForm 的重试已为每刻。表单的生成本身耗时很小。
- 测试 104 条。演示：每次「点我」发出 hello 事件，脚本播放音效、每 5 次给一颗绿宝石。
- 1.42.0 真机：一次出现异常——第一次打开时吞掉两次点击；倒计时卡在 1，多点一下「点我」才显示 0；倒计时过程中点右上角的关闭，有时关不掉。
  推测（未证实）：替换刷新时 closeAllForms 有时没有立即生效，旧表单仍显示（停在 1），新表单以 UserBusy 被拒并重试；期间点击旧表单，触发又一次替换才成功。
  处理（1.43.0）：①运行时加诊断记录（最近 60 条：显示、结果、推迟、替换、重试、关闭，带时间），测试脚本 /scriptevent cui:dump 打印；
  ②替换刷新的新表单遇到 UserBusy 时，重试前再 closeAllForms 一次（只用于刷新）。待用户复现后看记录定位。

## 20. 第二轮读者反馈后的 API 修订（2026-11，用户确认「可以的」）

2. **统一的名字空间**：视图从一个对象中解构 props、state、computed 的值与 methods（以及工具 button、close、link、back、next、prev、page）。四者之间、以及与工具名之间不能重名，否则构建报错。取代「computed 与 prop 同名即提供其值」。视图读取的 state / computed 也经由表单按钮传递（按需分配：视图用到才分配）；预览的默认值：state() 的初始值、computed 用初始状态计算（出错则为空）。

4. **深层响应式**：state 中的普通对象与数组用嵌套的 Proxy 跟踪（push、属性修改都触发更新）；类的实例（游戏对象、Timer）不跟踪。删除 `this.refresh()` 的必要性（保留方法）。

### 20.1 计时实验 1.59.0 的真机结果与修正（1.60.0）

- 现象：进行中时倒计时背后多一列不动的数字（重新打开时更新）；暂停时倒计时整个消失；进度条走满后倒计时仍在滚动（停在 0 滚一段时间才停），暂停过的更久。

- 原因 2（确定）：动画时长在构建时定为总时长，每次打开都播满；计时结束后不会停在「完成」。修正：运行时记下显示中进行着的计时器最早结束的时刻，到时刷新一次（显示 D）。

### 20.2 计时实验 1.60.0 的真机结果与修正（1.61.0）

## 21. 统一的页面写法（2026-11，用户确认「应该可以了」）

目标：单页、多页、选项卡、组件写出来是同一种样子——「函数返回一个 Page，往里面 add() 元素」。视图不再接收会变化的参数。

**定义**：`defineUI({ id, props, state, computed, methods, onOpen, onUpdate, onClose, timerEndRefresh, page })`。
- `page`：根页面函数 `(data) => Page`。`data` 只含使用者在 props / state / computed / methods 中定义的名字（数据占位与方法引用），框架不放任何东西进去，没有保留名。
- 删除 `defineScreen`、`view`、`pages`、`start`、`layout`，以及视图参数中的 `button`、`close`、`pages`、`tabs`。
- 返回的对象（类名仍为 Screen）照旧有 open / close / isOpen / on / off。

**元素**（都从 'bedrock-cui' 导入，用 new 创建、add() 放入）：
| 元素 | 作用 |
|---|---|
| `Page` | 一页内容（Panel 的子类，语义上的「页」）；在页面组中缺省铺满页面组 |
| `Router({ 名称: 页面函数 })` | 一组子页面，服务端切换；`.startAt(名称)` |
| `Tabs({ 名称: 页面函数 })` | 一组子页面，客户端切换；`.startAt(名称)` |
| `Link(名称)` | 跳到子页面 |
| `Back()`、`Prev()`、`Next()` | 返回 / 上一页 / 下一页；无处可去时自动隐藏 |
| `Close()` | 关闭界面 |
| `Button().onClick(方法, …参数)` | 调用方法；不绑定方法时是纯粹的界面按钮 |
- 跳转元素与 Button 一样有 `default`、`hover`、`pressed` 状态，另有 `selected`（目标页正在显示时显示，用于高亮当前标签 / 页）。
- 页面组的子页面函数同样是 `(data) => Page`，构建时由框架调用（逐层展开，组可以嵌套：Tabs 可以放在 Router 的页里）。

**跳转元素找所属的页面组**：先沿父级向上找含有该名称（Link）或任意（Back / Prev / Next）的组；在公共部分时，在整棵树中找含有该名称的组；名称重复时构建报错，提示写成 `new Link('组名:页名')`（组名即页面组元素的 setName）。

**实现要点**：
- Router 的页面可见性沿用服务端翻页（标题带页名）；跳转改为运行时处理的按钮（__link / __back / __next / __prev，清单记按钮所属的页）。跳转后焦点给「新页中动作相同的按钮」（同一个公共部分的按钮序号不变），保证鼠标不动连续点击；自动加「原地不动」按钮。Prev / Next 在首页 / 末页的页内元素编译时隐藏；公共部分的 Prev / Next / Back 由运行时在不可用时不写标记（隐藏）。
- Tabs 编译为客户端开关组（原 Pages 的客户端用法）；Link 在 Tabs 中编译为开关（unchecked → default、hover、checked → selected）。Tabs 中的 Next / Prev 允许但静态检查警告（客户端连续点击不可靠，真机）；Tabs 的状态在界面重新打开后回到 startAt（服务端读不到开关状态）。
- 第一版每个界面最多一个 Router；Tabs 数量不限。
- Button：绑定了 onClick 的编译为服务端按钮（普通版 + 聚焦版，同 ScreenButton），序号在构建时分配；未绑定的仍是界面内部的按钮。

**命名**：defineUI；「界面」一词保留（「容器」与 Panel 及 Minecraft 的箱子类界面冲突，用户同意）。
**影响**：不兼容（未发布）。模板、示例、测试包的界面文件、单元测试、手册（界面文件、数据、逻辑、页面、选项卡、计时显示、快速上手、README 等）全部改写。计时 HUD（defineTimerHud）是独立接口，不在此次范围。

### 21.4 小数能否参与运算（2026-11-19，GPT 的分析）

- 远端 338b0fb（用户与 GPT）：ProgressBar 的数值模式 `new ProgressBar(数值, 上限)`（脚本算好整数千分比再传入）、计时器的输入校验、表单等待结果时打开另一个界面的处理。拉取后 146 条测试通过。
- GPT 指出：「运算只有整数」说得太宽。已验证的只是：表单文字转换得到整数，整数之间的除法是整数除法（1.51.0：1÷4、25÷100 为 0），小数文字转换后不可用；固定的小数属性（裁剪 0.25）正常；原版经验条把引擎给的小数 #exp_progress 直接绑定到 #clip_ratio。小数常数参与运算的结果从未单独验证。
- 手册、真机规则与 decimal-arith 的提示改为区分「已验证」与「待确认」。
- 1.67.0 比较实验加 R–U（n = 5）：R (5÷20)>0 对照、S (5×0.1)>0、T (5÷12.5)>0、U (5÷2)=2 对照。按整数算：R、S、T 隐藏，U 显示；支持小数：R、S、T 显示，U 隐藏。GPT 建议的 property_bag 写 4.0 无法实现（编译输出经 JSON 序列化，4.0 写成 4），改用本身就是小数的常数。比较实验改为两列。
